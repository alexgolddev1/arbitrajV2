# Сервис трейдера

Каталог содержит компоненты, которые передают подтверждённые возможности от WebSocket-скринера в сервис трейдера. Получив JSON, трейдер проверяет маршрут перевода между биржами и заново получает spot-котировки. Итог и причины отклонения записываются в отдельный лог `log/trader.log`. Выставление ордеров пока не реализовано.

## Как проходит возможность

1. WebSocket-скринер находит связку, которая проходит порог спреда, и начинает считать её непрерывное время жизни.
2. Если связка сохраняется не меньше `MIN_OPPORTUNITY_LIFETIME_SECONDS`, скринер формирует JSON и добавляет его в таблицу MySQL `trader_signals`.
3. Отправка выполняется один раз на эпизод возможности и порог спреда. Уникальный ключ в очереди защищает от дублирования.
4. Контейнер `trader` забирает сообщение и проверяет, что для валюты возможен вывод с биржи покупки и ввод на биржу продажи через одну сеть. Если API одной стороны не вернул сеть, используется допущение из `exchange_networks.py`; явно отключённый вывод или ввод не допускается.
5. После проверки сети трейдер заново запрашивает лучшие `ask` покупки и `bid` продажи через публичные spot API. Возможность считается актуальной, если свежий спред не ниже минимального порога скринера, по умолчанию `0.5%`.

Значение 15 секунд — порог непрерывной жизни возможности, а не период отправки сигналов. Проверка MySQL-очереди потребителем выполняется отдельно, с интервалом `SIGNAL_POLL_INTERVAL_SECONDS`.

## Модули

| Файл | Ответственность |
| --- | --- |
| `config.py` | Порог времени жизни и интервал проверки очереди. |
| `signals.py` | JSON-структура, формирование сообщения и проверка обязательных полей. |
| `queue.py` | Запись сообщения в MySQL, атомарное получение и фиксация результата обработки. |
| `network_check.py` | Проверка сети с доступными выводом и вводом на биржах. |
| `fees.py` | Получение персональных spot-ставок maker/taker аккаунта с бирж и кэширование ответов. |
| `market_data.py` | Повторное получение spot-котировок и симуляция рыночного исполнения продажи по уровням bid стакана. |
| `processor.py` | Последовательность проверок сети, комиссий, свежего спреда и передачи сделки торговому режиму. |
| `trade.py` | Расчёт результата после двух taker-комиссий; тренировочная симуляция или заглушка рабочего режима. |
| `service.py` | Инициализация БД и цикл потребителя очереди. |
| `logging_setup.py` | Консольный лог и отдельный ротируемый `trader.log`. |
| `tran_emulation.py` | Профили и эмуляция времени перевода между биржами. |
| `exchange_networks.py` | Получение сетей бирж и сопоставление маршрутов перевода. |

WebSocket-монитор скринера вызывает `signals.build_opportunity_signal()`, затем передаёт результат в `queue.enqueue()`. Это отделяет наблюдение за рынком от формата сообщения и дальнейшей обработки трейдером.

## Формат сообщения

Пример JSON в очереди:

```json
{
  "event": "opportunity_matured",
  "lifetime_id": 481,
  "source_market_id": 1396616,
  "source_pair": "MBL/USDT",
  "threshold_percent": "1",
  "spread_percent": "1.03",
  "max_spread_percent": "1.17",
  "buy": {
    "exchange": "Binance",
    "market_pair": "MBL/USDT",
    "price": "0.000699",
    "available_base_quantity": "250000",
    "available_quote_amount": "174.75"
  },
  "sell": {
    "exchange": "MEXC",
    "market_pair": "MBL/USDT",
    "price": "0.0007062",
    "available_base_quantity": "200000",
    "available_quote_amount": "141.24"
  },
  "network": "UNKNOWN",
  "estimated_transfer_seconds": 300,
  "opportunity_started_at_utc": "2026-10-18 00:45:14",
  "lifetime_seconds": 15.2
}
```

Цены и объёмы передаются строками, чтобы не терять точность десятичных значений.

## Настройки

Настройки находятся в `config.py`:

| Параметр | По умолчанию | Назначение |
| --- | ---: | --- |
| `MIN_OPPORTUNITY_LIFETIME_SECONDS` | `15` | Сколько секунд возможность должна непрерывно подтверждаться до отправки трейдеру. |
| `SIGNAL_POLL_INTERVAL_SECONDS` | `0.5` | Как часто потребитель проверяет очередь MySQL на новые сообщения. |
| `MARKET_DATA_TIMEOUT_SECONDS` | `5` | Таймаут запроса свежей котировки к бирже. |
| `NETWORK_CACHE_TTL_SECONDS` | `60` | Время кэширования результатов проверки сетей для той же валюты и маршрута. |
| `FEE_CACHE_TTL_SECONDS` | `300` | Время кэширования maker/taker ставок аккаунта по бирже и спотовой паре. |
| `TRAINING_MODE` | `1` | Режим тренировки (виртуальная торговля); `0` отключает тренировочный режим. |
| `INITIAL_BALANCE_USD` | `100` | Начальный баланс в долларах, записывается при первом старте и не сбрасывается при перезапуске. |

В Docker Compose значения можно переопределить переменными `TRADER_MIN_OPPORTUNITY_LIFETIME_SECONDS`, `TRADER_SIGNAL_POLL_INTERVAL_SECONDS`, `TRADER_MARKET_DATA_TIMEOUT_SECONDS`, `TRADER_NETWORK_CACHE_TTL_SECONDS`, `TRADER_FEE_CACHE_TTL_SECONDS`, `TRADER_TRAINING_MODE` и `TRADER_INITIAL_BALANCE_USD`. При первом старте создаётся запись в `trader_account`; существующий баланс сохраняется, а режим обновляется согласно конфигурации.

Проверка сетей и запрос персональных торговых ставок используют API-ключи бирж из корневого `.env` (`BINANCE_API_KEY`/`BINANCE_API_SECRET`, `BYBIT_API_KEY`/`BYBIT_API_SECRET`, `OKX_API_KEY`/`OKX_API_SECRET`/`OKX_API_PASSPHRASE`, `MEXC_API_KEY`/`MEXC_API_SECRET`). Для ставок аккаунту нужны разрешения чтения торговых данных. После выбора маршрута трейдер запрашивает maker/taker комиссию на бирже покупки и продажи для spot-пары. Для оценки предполагается taker-комиссия на обеих сторонах; комиссия за перевод и проскальзывание пока не учитываются. Публичные spot-котировки запрашиваются без ключей.

В тренировочном режиме размер операции ограничивается сохранённым USD-балансом и доступным объёмом ask на покупке. Если после двух taker-комиссий ожидается прибыль, в `trader_training_settlements` записывается ожидающая симуляция, но баланс пока не меняется. После эмулируемой задержки сети трейдер повторно получает стакан продажи и исполняет симуляцию как рыночный ордер: забирает объём последовательно с лучших bid и следующих уровней, учитывая фактическую среднюю цену и выручку. Если объёма всего полученного стакана недостаточно для продажи, проверка повторяется через 15 секунд. Баланс обновляется одной транзакцией только после успешной симуляции продажи. В обычном режиме прибыльная возможность пока только проходит оценку: трейдер пишет `Функционал не реализован` и не отправляет ордер.

## Запуск и логи

Трейдер входит в обычный запуск Compose. Чтобы отдельно пересобрать и запустить его вместе со скринером:

```powershell
docker compose up -d --build app trader
```

Посмотреть сообщения обоих сервисов:

```powershell
docker compose logs -f app trader
```

Полный журнал трейдера на хосте: `log/trader.log`. Файл ротируется при достижении 5 МБ; сохраняются пять предыдущих файлов.

Таблица `trader_signals` создаётся из корневого `schema.sql` при инициализации базы. Поле `status` принимает значения `pending`, `processing`, `processed` и `failed`. Если контейнер трейдера завершится после получения сообщения, зависший статус `processing` будет доступен для повторного получения через две минуты.

## Куда добавлять торговую логику

Проверки сигнала остаются в `processor.process_opportunity()`, а расчёт и выбор тренировочной/рабочей ветки — в `trade.process_trade()`. Перед реальными ордерами нужно дополнительно учесть комиссию перевода, проскальзывание, фактический баланс обеих бирж и валюту списания торговой комиссии.
